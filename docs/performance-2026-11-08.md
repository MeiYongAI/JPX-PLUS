# 战斗更新性能排查 — 2026-11-08

后续 2026.11.08.7 的重复监听、异步清理、战斗内策略调整和手动恢复测试见 [生命周期排查记录](battle-lifecycle-2026-11-08.md)。本页保留 .6 的测量，不将旧性能数据当作 .7 的重新测量结果。

本轮针对 2026.11.08.5（3161521）的战斗更新路径，修复发布为 2026.11.08.6。性能测量使用隔离 Chrome、合成战斗 DOM 和拦截的网络请求；未操作真实账号、安装中的脚本或实际战斗。

## 已确认的问题及修复

1. **数值读取触发布局**：快捷栏写入之后，getVitals 连续读取 HP、MP、SP 的 innerText。原生纯文本数值改用 textContent；若其他脚本添加了子元素，保留 innerText，避免把隐藏内容混入数值。
2. **重复日志序列化**：同一轮更新中的战斗记录和状态分析分别读取、清理、匹配整段日志。现在只在本次同步调用内共享一个快照；下次更新重新读取，既不跨轮缓存，也不延迟状态更新。最终结算的胜负判断也复用一次读取。
3. **重复追加提示**：当战斗节点被保留时，快捷栏、冷却、状态倒计时、怪物序号、信息和血量会再次追加。现在按原生节点复用 JPX 自有节点，仅在内容变化时写入；配置关闭、技能不可用、效果消失时同步处理。WeakMap/WeakSet 不会因索引本身永久保留被替换的旧节点。
4. **重复渲染影响判断**：JPX 追加的信息可能进入下一次怪物名称／等级读取；补出的隐藏效果可能被当作原生第七个图标。修复读取边界并单独标记合成效果，验证隐藏效果递减、失效和移除。
5. **无变化的日志分隔线**：已有 hr 不再重写，减少无意义 DOM mutation。

## 对比数据

每个场景、每个版本各跑 3 次，每次预热 15 轮、采样 80 轮；交替执行新旧版本。表内是三次运行各自中位数的平均值，单位毫秒。夹具构建不计入单次更新耗时，浏览器 LayoutCount 等辅助指标仍包含夹具构建及最终绘制，不能当作单次更新的纯布局成本。

| 离线场景 | 旧版 | 本轮 | 变化 |
| --- | ---: | ---: | ---: |
| 每次替换战斗 DOM，关闭附加显示 | 0.600 | 0.400 | 约减少 33% |
| 每次替换战斗 DOM，开启附加显示 | 1.367 | 1.067 | 约减少 22% |
| 每次替换战斗 DOM，2,000 行历史日志 | 3.433 | 1.900 | 约减少 45% |
| 保留同一批节点，连续更新 | 3.033 | 0.500 | 约减少 84% |

保留节点场景运行 95 轮后，战斗区域元素数由旧版的 16,436 降为 639；该结果说明重复追加被消除，**不表示真实游戏一定采用相同的节点保留方式**。本轮独立检查连续 100 次相同渲染：新增元素 0、战斗区域 DOM 写入 0、innerText 读取 0。正常完整替换场景仍需创建新显示节点，不应将重复渲染的零创建数套用到该场景。

开启附加显示的完整替换场景，三次 P95 平均值均约 2.83 ms，未观察到可靠的尾延迟改善；不要据中位数宣称所有延迟指标都有同比提升。

原始数据见 [battle-2026-11-08.json](performance/battle-2026-11-08.json)。记录的 candidate SHA-256 对应测量时内容；随后仅将主脚本两处版本元数据由 .5 提升至 .6，运行逻辑未变。

## 复跑

安装开发依赖后，PowerShell 示例：

```powershell
$env:PLAYWRIGHT_CHANNEL = 'chrome'
$env:JPX_PERF_BASELINE = 'C:/path/to/2026.11.08.5.user.js'
$env:JPX_PERF_OUTPUT = '.test-output/battle-profile.json'
npm run profile:battle
npm test
```

未设置 JPX_PERF_BASELINE 时仅测当前脚本。时间数据不作为自动测试阈值；确定性检查依赖实际操作次数与结果。
