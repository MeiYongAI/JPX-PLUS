# 配置库首次读取优化 — 2026-11-08

发布版本：2026.11.08.10；对照版本：2026.11.08.9（d0e688e）。

外部报告指出，控制面板与战斗流派判断的首次调用会通过 refreshJpxSelectedConfig 进入完整配置库验证。这条调用链在 .9 中仍存在；既有页内缓存无法跨越未开启 AJAX 时的整页过轮。本次针对已核实的代码成本优化，没有把报告中的 400 ms 当成本机已经复现的结果。

## 具体修改

1. **区分 JSON 数据与任意对象。** 存档 JSON.parse 后已是独立的数据树，不再通过通用 encode/clone 检查访问器、原型、稀疏数组和循环引用后再复制。改用 JSON 专用遍历，仍检查禁止键名、有限数值、节点数、深度、数组长度，以及原始/规范化 JSON 的大小。保存和迁移接收的任意对象仍使用原有严格检查。
2. **每条配置只规范化一次。** 完整存档已经通过结构检查，在其内部独立对象上执行原有版本检查、规则校验和兼容迁移，保留单个 envelope 大小限制，不再逐条深拷贝后重新遍历。
3. **引用校验使用索引。** 遍历 entries 时构建 Map，applied 和 bindings 按 ID 查找；重复 ID、缺失引用、过期 revision、重复绑定仍按原逻辑拒绝。
4. **读取所需部分。** 新增 readSelection(world)，完整验证后只复制该世界当前选中的 applied 记录。get(id) 只复制所需 entry；内部缓存对象不暴露。完整 readState 继续返回独立副本，且仅在需要时建立序列化缓存，后续完整读取仍复用它。
5. **保留选择一致性。** manager 仍核对 mode、当前 cfgBattle 与 applied 快照，仍保留页内选择缓存、跨标签应用时暂停战斗的行为。

没有添加独立持久化选择键，没有改变存档格式或后台加载配置。首次读取仍完整验证当前库；不会因为另一条未选中配置损坏而悄悄跳过检查。应用与回滚仍使用现有存储键，避免引入两个持久化状态之间的同步问题。

内部多保留一个经过验证的对象树，以减少热读时重新解析整库。它只缓存最近一次成功验证的库，不累积历史快照；完整库序列化缓存惰性建立。本次没有测量长期堆内存曲线。

## 对照测量

隔离桌面 Chrome、合成配置库与战斗 DOM、拦截所有网络响应，运行真实 initDo 和非 AJAX 原生页面跳转。每个场景每版本 3 组 × 5 次新文档初始化，交替版本顺序，共 150 个样本。下表为各场景 15 个样本的中位数，单位 ms。

| 场景 | .9 选择读取 | .10 选择读取 | .9 initDo | .10 initDo |
| --- | ---: | ---: | ---: | ---: |
| 992 KiB，简单规则，无显式选择 | 16.7 | 5.2 | 26.2 | 14.2 |
| 992 KiB，简单规则，有显式选择 | 16.2 | 5.8 | 25.3 | 15.1 |
| 992 KiB，多条件规则，无显式选择 | 26.8 | 7.2 | 36.1 | 16.5 |
| 992 KiB，多条件规则，有显式选择 | 27.1 | 7.2 | 36.0 | 16.1 |
| 2 MiB，多条件规则，2,000 绑定 | 52.8 | 14.5 | 62.1 | 24.1 |

合成库包含 40 或 80 份配置；简单模式每份 170 条空条件规则，多条件模式每份 44 条规则、每条 5 个条件。使用一个 description 字段补齐相同体积，字节量不代表相同对象数量。数据生成器见 tests/fixtures/config-archive.cjs。

所有新旧样本的初始化状态、模式、规则、统计和怪物数据逐项相等；保持手动状态、攻击/施法次数为零、每次初始化只读一次配置库、存档原文不变。原始数据 `docs/performance/config-read-2026-11-08.json` 仅保存在本地，不再随仓库发布。测量 SHA 对应发布前源码，随后仅修改两处版本字段，运行逻辑一致。

这些结果说明首次配置读取成本降低约 64%–73%，不是页面总加载时间或实战 TPS。未连接实际战斗、未使用报告人的原始配置库，也没有复现或证明解决其 400 ms 长任务。

## 复跑

安装项目开发依赖后，在 PowerShell 设置 JPX_PERF_BASELINE 为 .9 脚本路径，运行 npm run profile:config-read。可通过 JPX_CONFIG_READ_REPEATS / JPX_CONFIG_READ_ROUNDS 调整样本数，通过 JPX_CONFIG_READ_OUTPUT 指定输出文件。默认只测当前脚本；不设置脆弱的耗时通过阈值，正确性依靠结果和操作次数断言。

继续追踪实际 400 ms 报告需要脱敏配置库、完整 Performance trace、当时脚本和打点补丁。若还有可复现的较大首次成本，再评估存储拆分；必须同时覆盖旧数据迁移、选择一致性和失败回滚。
