## 复现与修复

| 问题 | 基线复现 | 修复与验证 |
| --- | --- | --- |
| 同一日志重复初始化 | 初始化三次后，一次变动处理 3 次 | 旧监听器断开，单次变动只处理 1 次 |
| 跨回合的尾随回调 | 排队后替换页面，旧回调仍处理新日志 1 次 | 取消定时器并检查回合代次及节点，旧回调处理 0 次 |
| 谜题期间残留工作 | 进入谜题仍执行旧日志回调 | 进入谜题时清理监听、数据库请求和待执行决策 |
| 缺少可选怪物数据库仍高频轮询 | 三次并发调用累计产生 72 个 10 ms 定时器（该次测量值） | 共用单个请求；缺少接口时在原有约 250 ms 窗口内最多 5 次、间隔 50 ms 探测，10 ms 定时器为 0 |
| 应用策略留下悬停恢复标记 | AJAX 重置后应用策略，恢复标记仍为 true | 应用时清理标记并关闭当次悬停门控，移动不再绕过暂停 |
| 应用后立即恢复重复决策 | 旧决策已排队，应用并恢复后同一目标点击 2 次 | 暂停、切换策略、换轮时取消旧决策；该序列只点击 1 次 |

接口已存在时仍保留原先约 10 ms 查询间隔和约 250 ms 等待窗口，避免放慢已安装插件的状态获取。缺少接口时也保留有界探测，覆盖插件稍晚初始化。查询结果只写回发起它的当前回合，旧请求完成不会清掉新请求。

Scan 之后怪物 ID 不变，但等级、攻击、类别或更新时间可能改变。现在刷新请求会比较实际使用字段的快照，也覆盖插件原地修改同一对象的情况。普通换轮仍拒绝上一轮相同 ID 的旧数据，不把旧回合信息填到新怪物上。关闭信息显示时仍维护供战斗条件使用的数据。

## 战斗内调整策略

新增测试覆盖完整战斗 DOM 与实际界面事件：

- 运行中应用另一套策略先暂停，恢复后的目标遵循新策略，仅执行一次。
- 修改规则、启用／禁用、撤销／重做、保存草稿不会直接替换当前执行规则；点击“更新并应用”后生效。
- 修改目标优先级或停止条件后，恢复可立即使用新值，无需等待下一次战斗日志。
- 跨标签应用同步新策略并暂停；已排队的日志仍可更新记录，但不会重新启动战斗。
- 多次 AJAX 换轮保留明确选择的策略，无重复决策。
- 手动快速暂停／恢复也会取消前一次尚未执行的决策。

## 手动补充状态后能否自动继续

**规则触发的 Stop 与用户主动暂停的含义不同。** Stop 保留自动战斗启用状态，只等待条件解除。手动补充后，只要游戏更新数值和日志，下一次处理会重新判断规则；HP／MP／SP 达到继续条件即可自动继续，无需重新进出控制面板。

新增 11 项恢复回归：AJAX 开关分别测试 HP、MP、SP（6 项），执行 AJAX 换轮后分别测试三种状态（3 项），主动暂停与应用新策略两种暂停边界（2 项）。补充仍不足时继续等待，恢复足够时只执行一次；主动暂停或应用策略之后，补充状态不会擅自恢复。

同样的 11 项测试在基线 .6 上也全部通过：这里验证的是原有自动恢复行为得到保留，没有把它误报为本轮才修好的缺陷。

AJAX 选项控制免刷新进入下一轮。进入新一轮仍遵循既有的启动／悬停门控；上述自动恢复指本轮已经启用自动战斗、随后被 Stop 条件挡住的情况。
