# 长战斗日志追加与过轮保存优化 — 2026-11-08

发布版本：2026.11.08.11；对照版本：2026.11.08.10（a5dcf28）。

本次只优化启用“记录完整战斗日志”后的历史追加与临时保存，不改变策略、自动行动、统计计算或完整日志格式。该选项默认关闭；未启用时没有这部分长历史成本，也不应预期获得同样收益。

## 修改和兼容边界

1. **追加不再复制全部历史。** 原先每次行动使用 concat 生成整个新数组，改为逐行 push 当前批次。历史越长，每次行动重复复制越昂贵；循环追加同时避免一次展开极大批次时的参数数量限制。
2. **保存只序列化新增部分。** 初始化恢复日志时保留读到的 JSON 文本作为已保存前缀；后续只对新增后缀进行 JSON.stringify，再构建完整 JSON 数组字符串。
3. **无变化的重复保存不再序列化或写日志键。** 仍读取实际存储键进行比较，外部删除、替换或清空不会让内部缓存误判为已保存。其行为和旧版一样：内存中的完整日志是当前页面保存的数据，不合并跨标签的其他战斗。
4. **成功写入后才更新保存位置。** 写入失败不推进检查点，下次成功保存包含全部尚未保存的条目。数组替换或长度缩短时重新完整序列化；非数组沿用删除旧键的处理。
5. **保留临走前最后一条记录。** storeTmp 原有 observer / throttle 待处理刷新照常执行，且不渲染或发起攻击。最终结算后的临时数据不被重新写回。

存储键仍为 jpx_battleLogRecord / jpx_battleLogRecord_isekai，值仍是完整 JSON 数组，旧版可以读取。没有裁剪、压缩、去重或省略历史；相同文本的新行动仍分别记录。Scan 嵌套表格、初始化行、轮末分隔符和汉化包装保持已有提取语义。特别是 Scan 内层 td 原有的独立记录行为未在本次调整。

序列化前缀依赖日志的内部只追加约定。生产代码只在初始化替换数组、记录器追加；插件和自定义策略 API 不暴露这个数组。缓存不会检测同一数组里旧条目的原位改写；若未来增加日志编辑功能，需要同时使检查点失效。

## 隔离浏览器对照

使用本机无头 Chrome、合成战斗 DOM 和日志，拦截所有网络。运行生产 battleRecorder / storeTmp；新旧版本交替，3 组，每个历史规模及开关状态各 12 次测量，共 **432 个批次样本**。每个批次追加 **200 次行动**、保存一次，再无变化保存一次；每组先预热 3 个批次。以下为 36 个样本的中位数，单位 ms。

每次行动生成 3 条日志；历史随批次增长，不在每个样本之前重置。所以“初始历史”是该组起点，不是每次保存的固定长度。第一份已保存检查点在计时前建立。计时包括日志 DOM 读取、战斗统计、完整字符串拼接、存储读取比较和实际写入；不含夹具构造、结果校验与导出。

## 仍然存在的成本

- localStorage 每次有新增仍需同步写完整字符串；缓存不会把大日志保存变成固定成本。无变化保存也有读取和字符串比较成本。
- 内存中保留一个最近成功保存的序列化前缀，加上原有日志数组。最大测试末尾为 109,003 条、5,000,028 个 ASCII 字符；这是文本长度，不是堆内存测量。没有测量长期堆增长或垃圾回收停顿。
- 存储配额和写入异常仍按原先抛出；新增回归验证的是失败后在当前页面重试不遗漏。没有声称配额已满、页面直接关闭时还能持久化成功。
- 未使用实际账号实战，未安装用户脚本、测量真实 TPS 或复现报告人的 400 ms 长任务；合成结果不能替代这些验证。
